# 实习能力链路表述（v4）—— 外设板：外设数据采集 + 数据转发

> **素材来源**：daily-2026-07-16 / 07-20 / 08-06 / 08-07 + 外设板移植.md + 本人口述补充
> **定位**：面向**嵌入式软件 / RTOS** 方向的**项目深挖**材料；口吻**谦逊但扎实**。
> **v4 变更**：① 技术栈补"RT-Thread 也只懂最基础"；② USB 定位改为"**代码基本全由 AI 完成，我的核心工作是给 AI 提供排查方向**"（附三个排查方向实例）；③ 帧率提升改为**三步：3Hz → 9Hz → 16Hz**，最终靠 **I2C DMA** 收尾。

## 〇、项目背景（一句话定位自己）

> 这是我实习公司一个**正在开发的新项目**里的一小块：整个系统有 **8~9 块板子**，我负责其中一块——**外设板**，作用一句话就是**外设数据的采集与转发**。我这边不只是调自己的板，还要和算法板（它是 USB 主机，收我发的数据）等其它板做跨板联调。所以这是一个"多板系统里负责一块板"的岗位，既有独立责任，也要懂周边板怎么配合。

## 一、主线（谦逊扎实版）

### 一句话

> 我负责外设板的数据采集与转发：采集侧打通 MLX90642 红外热成像、温湿度、红外接收，转发侧打通 USB CDC 虚拟串口，把数据可靠送到算法板。这两块我上手时**基础都不算好**——USB 之前完全没做过，MLX 全英手册读起来吃力，RT-Thread 我也只了解最基础的内容，比如大概怎么用一个外设。

### 展开版

外设板本质是一块数据中继板：上游是传感器，下游是算法板。我的工作是把「传感器 → 板内组包 → USB 转发 → 对端解析」整条链路做通、做稳、做到达标。技术栈是 RT-Thread + N32G435（Cortex-M4）。这个项目让我在两条线上成长最多：

- **USB CDC**：我承认 USB 底层代码**基本全部是用 AI 完成的**，我自己不会手写 USB 寄存器配置。但我做的一件重要的事是——**给 AI 提供排查方向**。比如创建 USB 相关线程时程序崩溃，我让 AI 去查线程的栈/优先级配置是否合理；USB 速率远不到预期，我让 AI 排查是不是用了死等/阻塞动作；AI 反馈"空满"时，我让它进一步判断是不是"没开 USB 但一直在推队列"导致的。**"知道该往哪个方向查"反而是这个过程中我收获最大的能力**，也让我把 USB 的枚举、PMA、bulk IN、1ms 轮询这些概念一点点搞明白了。
- **MLX90642**：配置小坑多。最深的技术难点是 **I2C 在 1536 字节大吞吐下逐字节轮询要占 CPU 约 35ms**，会阻塞 RTOS、挤占其它线程；**和 USB 一起跑时**（USB 也要及时响应主机事务）给整个项目带来很大困难。这是后来给 I2C 加 DMA 的原因。此外还有撕裂帧问题。

## 二、USB CDC 转发 —— 四阶段链路（项目深挖主战场）

> 先说清我的工作方式：**USB 驱动代码基本全部用 AI 完成，我的核心贡献是给排查方向 + 逐步搞懂协议**。这条线的价值不在于"我写了多少驱动"，而在于"我能在每一步踩坑时，判断问题可能出在哪、该往哪个方向查"。下面四个阶段对应四类坑，每个阶段我都给 AI 指了一个方向。

### 阶段 1：成功枚举（AI 实现，我把概念搞懂）

- USB 驱动代码由 AI 生成，对接 RT-Thread `udcd` 框架。
- 我这边真正收获的是把 USB FS 的**三层模型（EPR 端点寄存器 / PMA 包缓冲区 / ISTR 中断状态）**、以及几个关键约束搞清楚：
  1. **48MHz 时钟约束**：USB FS 必须精确 48MHz，而 N32G435 **没有 HSI48**，只能从主 PLL 分频 → 主频必须改 108→**96MHz**。
  2. **板间连接细节**：外设板与算法板之间是 3 芯连接器（只有 DP/DM/GND，无 VBUS），DP 上拉走 **PA1 软件软连接**。
- 踩过的坑：AI 给过一次硬件幻觉（把 STM32F0/L4 的 HSI48 套到 N32G435 上），我意识到**不能全信 AI 关于硬件特性的说法**，要用源码 / 寄存器核实。
- 结果：枚举成功，Windows 识别出虚拟串口。

### 阶段 2：枚举不崩溃（我给 AI 的方向：查线程配置是否合理）

- 现象：**创建 USB 相关线程 / 初始化后程序崩溃**，反复重启进不了主程序。
- 我给的排查方向：**让 AI 查线程的栈 / 优先级配置是否合理**。
- 最终定位的根因：RT-Thread 的 vcom 线程优先级 = **16**，而工程为省 RAM 把 `RT_THREAD_PRIORITY_MAX` 设成 **10**（合法只有 0~9）。调度器用优先级当数组下标 `rt_thread_priority_table[priority]`，**vcom 的 16 越界了 6 项**，`rt_list_insert_after` 往数组外写指针 → 踩坏相邻就绪节点 → 调度器访问垃圾指针 → **bus fault**。这是确定性故障（编译期常量，每次必崩）。
- 修复：`RT_THREAD_PRIORITY_MAX` 10→32。
- 我的复盘：这是一个"为省 RAM"的 RTOS 配置宏，在接入 USB 这种新子系统时突然引爆；**症状点（fault）和病因点（优先级表）隔得很远**。也让我体会到读内核数据结构比瞎猜有用。

### 阶段 3：成功发送（枚举完美但 0 帧 / ep_in=0 困局）

- 现象：枚举完全成功（Windows 显示 "RTT Virtual Serial" COM 口），但 PC 收到 **0 帧红外数据**；串口助手还一打开就崩。
- 排查过程（这步踩的坑很典型）：
  1. **先排除工具 bug**：串口助手崩溃是它在枚举阶段读 `iProduct` 字符串描述符时的兼容性 bug（残留文件句柄还污染了端口），换 pyserial 验证板子本身没问题。
  2. **数据流诊断逐层缩小**：`usb_status` 寄存器快照显示 EP1 `TX=VALID`（设备 armed 数据待发）但 `ep_in=0`（CTR_TX 中断一次没触发，主机从未 ACK 过 EP1 IN 包）。
  3. **PMA dump**：直接读 USB 包缓冲区，看到真实红外原始值（÷50 ≈ 30~31°C）→ **证明 task_ir→vcom→PMA 整条数据链是通的**，问题在主机侧。
  4. **撞到 USB IP 的架构限制**：F103-class USB IP 只产生"主机 ACK"中断（CTR_TX），"主机发 IN 令牌"本身没有中断 → `ep_in=0` 在板内**无法区分**"主机没发 IN"还是"发了但 CRC 错"。
  5. **上逻辑分析仪**（LA1016 + USB FS 协议解码）：在 D+/D- 上物理抓包，这是唯一能区分主机行为的工具。
- 附带踩的坑：诊断代码用裸指针读未配置端点的 PMA → 又触发一次 bus fault（教训：访问外设内存前要先校验地址范围）；发现 CDC ringbuffer `CDC_RX_BUFSIZE=128` **截断了 1546B 的红外帧**。
- 我的复盘：USB 是**严格的主机发起协议**，设备完全被动，"设备没准备好"和"主机没来取"必须在总线上区分——这个认知对后面所有 USB 吞吐问题的排查都很关键。

### 阶段 4：提升发送速率（三个吞吐瓶颈）

> 三件事，都是我边踩边学、给 AI 指方向的过程中解决的，未必是最优解，但在这个项目里验证有效。

**瓶颈 1：发送"死等" → ISR 续发（我给 AI 的方向：查是否有死等/阻塞动作）**
- 现象：USB 速率远不到预期（只有约 **3Hz** 交付）。
- 我给的排查方向：让 AI 排查发送路径上是不是用了**死等 / 阻塞**动作。
- 定位：vcom 发送线程是**死等**模式——每发一包就阻塞等 `rt_completion_wait`（上一包被主机 ACK / 或 1s 超时）才继续，一个包一个包串行走，USB 链路大部分时间在等。
- 修复：在**发送完成（CTR_TX）中断里通过续发（`_usb_ep_in_continue`）直接接上下一段数据**，配合双缓冲（一个缓冲在发送时，另一个在装填），把"准备下一包"从线程挪进完成回调。
- 结果：帧率从 **3Hz → 9Hz**。

**瓶颈 2：线程优先级分配不合理，vcom 被挤占**
- 现象：vcom 发送线程优先级被设成了 **8**，而同板其它采集/发送任务优先级都在 **2~4**（RT-Thread 里数字越小优先级越高）——**vcom 被甩到最低**，被更高优先级的任务持续挤占，数据发不出去。
- 修正：重新梳理线程优先级，给 USB 发送链留出调度窗口后正常。
- 我的复盘：RTOS 里**优先级是资源**，分配不合理会饿死关键路径；这和阶段 2 呼应——优先级既是隐患（越界）也是瓶颈（被挤占）。

**瓶颈 3：背压 —— 链路是好的，但换框架后没有正确使用（我给 AI 的方向：空满时进一步判断是否"没开 USB 但一直在推队列"）**
- 现象：AI 反馈队列"**空满**"（`mq_send failed` 丢帧）。
- 我给的排查方向：让它进一步判断是不是**"没开 USB，但数据一直在往队列里推"**导致的。
- 背景：数据发送链路最初是"USB 默认不打开、由 PC 打开（DTR 拉高）后再推"的一版，是可行的；后来换成了**"推送队列 + 统一取队列发送"框架**（`task_comm_soc_boost` 推队列 + `task_comm_soc_tx` 组包发送），**换框架时没有保留"USB 未打开就不推送队列"的操作** → PC 没开串口时，数据仍按节拍往队列里灌 → 队列/缓冲区被塞满 → 丢帧。
- 本质：**链路本身是好的，问题是用错了——换框架时漏配了原有的前置条件（未连接不推送）**。
- 修复（源头门控）：在数据注入源头第一行查 `vcom_is_connected()`（复用驱动已有的 DTR 连接标志），未连接不组包不入队，连接瞬间数据流立刻恢复。
- 对比：在消费侧（发送 drain）做丢弃 vs 在注入侧（源头）做门控——后者更干净，未连接时队列保持空，还从根上避免了一个 request 复用竞态。

## 三、MLX90642 采集 —— I2C 大吞吐阻塞 RTOS + 撕裂帧

### 难点性质

- 配置小坑多，**全英手册阅读有难度**（datasheet 的读窗模型、速率-刷新率配对表、坏像素寄存器都是英文精读出来的）。
- 最深的技术难点：**I2C 在如此大的数据量下容易阻塞 RTOS**——前期专注 USB 且单线程验证，**漏开了 DMA**，导致 I2C 逐字节轮询读 1536 字节要占 CPU 约 35ms，不仅速率上不去，还**挤占了其它线程**；**跟 USB 一起跑时**给整个项目带来很大困难。

### 帧率提升的三步（重要，体现"每一步解决什么"）

```
3Hz    USB 没有加续发（发送死等，速率上不去）
 │    + ISR 续发 / 双缓冲
 ▼
9Hz    USB 续发生效，但"空满"未解决 + I2C 还没上 DMA
 │      → 队列满丢帧，且 I2C 逐字节轮询占 CPU → 撕裂帧多
 ▼
16Hz   + I2C DMA：读帧不再占 CPU，I2C 不阻塞调度，撕裂消失
        → 最终达标 16Hz
```

### 技术点 1：撕裂检测（读窗模型 + 读后二次校验）

**我遇到的问题**：4Hz 刷新率却出现 21.4% 撕裂帧，坏像素集中在 row=22 一整行（idx 672~681 连续 10 个像素）。我一开始不确定是坏帧判断有问题、还是 I2C 链路有问题。

**我的做法**：
1. 先用 `mlx_defect_test.py` 从 USB CDC 采帧统计，把坏像素按"出现次数 / 总帧数"排序做**频率直方图**——发现是**一整行连续越界**而不是分散位错，直接判定为"整行撕裂"（系统性故障）而非随机错误或硬件坏点。
2. 读 datasheet 建立**读窗模型**：FLAGS 寄存器 0x3C14 有三个关键位——B0=BUSY（DSP 运算中）、B8=READY（温度数据可读）、B9=FRAME_UPDATE（帧数据更新中）。**安全的读窗 = READY=1 && !BUSY && !FRAME_UPDATE**。另一个关键语义：**读 TO_DATA(0x342C) 会自动清除 READY**——这是后面做检测的基础。
3. 重写 `MLX90642_GetFrameContinuous()`：读窗前轮询"读窗打开"再读；读完后**二次查 READY**——若已被清，说明读帧期间传感器刷新了 → 返回撕裂错误（`MLX90642_TEAR_ERR`），上层 `task_ir` **丢弃该帧立即重试、不计入失败计数**。

**为什么这么做**：如果只调坏像素阈值，撕裂帧会以"半旧半新"的混合数据上报——坏像素数量恰好低于阈值时**静默通过**，温度图出现整行伪影，肉眼极难发现（温度值都在合理范围）。只有显式检测 READY 被清除，才能把撕裂从**隐性数据错误变成显式丢弃**。

**验证结果**：撕裂帧从"悄悄混进数据"变成"检测到就丢、下帧重试"，坏帧率大幅收敛。

### 技术点 2：相位锁定（从"相位彩票"到"相位锚定"）

**我遇到的问题**：撕裂修好后，交付帧率仍没到源 16Hz。用诊断计数器（新增 `MOD_ID_IR_DIAG_FB` 上报 11 个 u32）区分出两个独立失败模式：**读窗漏采（window-miss）** 和 **抢占破坏（preemption corruption）**。针对读窗漏采，我一开始试着调任务优先级 / tick——结果只是"相位彩票"：改变采样相位与传感器时钟的相对关系，反而出现系统性 sawtooth 漂移（132/199/266/400ms 间隔），更糟。

**我的做法**：
1. 记录"上次抓窗成功时刻" `g_mlx_win_open_tick`。
2. 睡到 `(anchor + period − lead)` 再醒来——即按传感器刷新周期推算下次读窗开启时间，**提前一点醒来**。
3. 用 `n32_udelay(100µs)` **紧轮询抓窗**，抓到即读，每帧**重锚定**（把漂移纠回来）。
4. 封装成 `MLX90642_GetFrameContinuousLocked(slaveAddr, pixVal, win_period_ms, win_lead_ms, ...)`。

**原理 / 教训**：对**自由运行**的传感器，改任务优先级只是改变采样相位，**不解决窗口漏采**。"相位彩票"的教训是：**确定性问题要用确定性方法（相位锚定）解决**，而不是靠调整调度去碰运气。

### 技术点 3：I2C DMA 化（把 35ms 从 CPU 剥离）+ 子集匹配（ISR 风暴，最深根因）

**我遇到的问题**：9Hz 阶段撕裂帧多——因为 I2C 还是**逐字节轮询**读 1536 字节，占 CPU 约 35ms，期间被 prio-2 的 soc_tx（每 1ms 运行）和 USBD 抢占 → I2C DR 被覆盖（OVR）/ 读流被拉长 → 像素垃圾；同时它占着 CPU 也拖慢了整体节奏。**给 I2C 加上 DMA 后，读帧不再占 CPU，撕裂消失，帧率最终到 16Hz**。

**我的做法（I2C DMA / 中断化改造）**：
1. 把逐字节轮询改成**中断 / DMA 驱动**读取：数据搬移交给硬件，读帧约 35ms 内 CPU 完全空闲，boost / 发送线程可以运行。
2. 把 `I2C1_EV` 抢占优先级提到 0（`NVIC_PriorityGroup_2`，2 位抢占 + 2 位子优先级；USB_LP=prio1、IR EXTI=3）——只有 USB ISR 可能抢占 I2C EV。
3. 认识到 **OVR 的 25µs 死线**：400kHz 下每字节约 22.5µs，ISR 延迟超过这个时间 DR 就溢出、丢字节。

**我的做法（子集匹配修 ISR 风暴）**：
1. 读驱动源码发现：`I2C_GetLastEvent` 返回 `(STS1|STS2) & 0x00FFFFFF`，**包含全部错误标志**（OVR=0x800、ACKFAIL=0x400、ARLOST=0x200、BUSERR=0x100）。
2. 原 ISR 用**精确相等**判断 `if (ev != EV7(0x30040) && ev != SFT(0x30044)) return;`——一旦 OVR 置位，`lastevent = RxNE|OVR = 0x30840`，既 ≠ EV7 也 ≠ SFT → ISR return 但 **RxNE 没被读走** → I2C EV 中断线保持置位 → **prio-0 ISR 无限重入风暴** → SysTick / 所有线程饿死 → main() 喂不了 IWDG → 2s 后看门狗复位 → USB CDC 掉线。
3. 修复：改**子集匹配**——只要 RXDATNE（RxNE）就位就读 DR，忽略多余错误标志，并加 `g_mlx_ovr_cnt` 计数器记录 OVR 是否发生过：
   ```c
   if (I2C_GetFlag(I2C1, I2C_FLAG_RXDATNE)) {   /* 只要 RxNE，忽略错误标志 */
       data = MLX_I2C->DR;
       g_mlx_ovr_cnt++;                          /* 记录 OVR 是否发生过 */
   }
   ```
4. 验证：修复前撕裂 1 次即冻结；修复后 **120s 零撕裂、25.3KB/s 稳定、ok=9241 fail=0、max_gap=149ms**。

**为什么危险 / 我的复盘**：这是"**偶发但必然**"的中断错误——满载下任何一次偶发 OVR 都会把系统带入 ISR 风暴，单次测试可能全绿，**压测才暴露**。而且**中断路径与轮询路径的匹配语义必须一致**（都用子集匹配）——轮询路径用 `I2C_CheckEvent` 是子集匹配所以从来没炸过，差别就在这一个位掩码的语义上，后果却从"丢一个字节"放大到"整个系统复位"。**症状点（USB 掉线）和病因点（I2C ISR）跨模块**，不追到 ISR 根本找不到。

### 撕裂性质的演变（体现工程递进）

```
致命（错位）  →  可恢复（内容污染）  →  零撕裂
I2C 丢字节      读窗被 FRAME_UPDATE 覆盖   120s 压测 ok=9241 fail=0
（精确匹配炸机）  （检测即丢弃重试）
```

## 四、可量化的硬指标（面试必背）

| 指标 | 数值 |

## 五、可转化为面试题的知识点（埋点）

1. **USB 设备枚举流程？** → 总线复位 → GET_DESCRIPTOR(device)@addr0 → SET_ADDRESS → GET_DESCRIPTOR(config) → SET_CONFIGURATION → CDC 特有 SET_CONTROL_LINE_STATE(DTR) → usbser 免驱出 COM。
2. **为什么 USB 需要 48MHz？N32G435 怎么给？** → FS 位时钟 48÷8=6MHz、NRZI 需要精确时钟；N32G435 无 HSI48，只能主 PLL 分频，故主频须 48/72/96MHz 之一。
3. **`ep_in=0` 为什么板内无法定论？** → F103-class USB IP 只产生"主机 ACK"中断，主机发 IN 令牌无中断；板内无法区分"主机没发" vs "发了 CRC 错"，只能逻辑分析仪抓 D+/D-。
4. **RT-Thread 开机 bus fault 怎么定位？** → dump 寄存器 → fromelf 反汇编搜 pc → 找垃圾寄存器值 → 反推被踩的数据结构 → 二分法。IMPRECISERR 是延迟写、pc 不是真凶。
5. **RT-Thread 线程优先级为什么不能超过 MAX？** → `rt_thread_priority_table[MAX]` 用优先级当下标，越界访问踩内存；省 RAM 的 MAX=10 在接入 USB（vcom prio=16）时引爆。
6. **USB bulk IN 吞吐为什么上不去？设备"猛发"有用吗？** → FS 每 1ms 主机轮询一次 IN + 64B 包长 + 握手开销；设备无法主动发送，只能等主机 poll。带宽 ≠ 吞吐。
7. **USB 发送"死等"怎么优化？** → 在 CTR_TX 中断里续发（`_usb_ep_in_continue`）/ 双缓冲提前装填，把等待从链路上剥离（3Hz→9Hz）。
8. **为什么换"推送队列"框架后会丢帧？** → 换框架但没保留"USB 未打开不推送"的前置条件，PC 未开串口时队列被灌满；修复是在注入源头查连接标志做门控。
9. **I2C 撕裂帧怎么检测？** → 读窗模型（READY/BUSY/FRAME_UPDATE），读后二次查 READY，撕裂丢弃重试 + 相位锁定。
10. **I2C 大吞吐为什么阻塞 RTOS？加了 DMA 后为什么到 16Hz？** → 逐字节轮询读 1536B 占 CPU 35ms、漏开 DMA；DMA 化后读帧不占 CPU、撕裂消失（9Hz→16Hz）。
11. **I2C 400kHz 位错误根因？** → 上拉电阻不当，Fast Mode 要求 SDA 上升沿 <300ns，需外部 ≤4.7kΩ 上拉。
12. **ISR 里 I2C 事件标志为什么要子集匹配？** → `I2C_GetLastEvent` 返回值含错误标志（OVR/ACKFAIL/ARLOST/BUSERR），精确相等失配 → RxNE 未读 → 中断线保持 → ISR 风暴 → IWDG 复位。
13. **验证脚本可信度边界？** → 自报计数器（frame_no）必须配外部实证（像素内容校验和），证据要独立于被测系统。

## 二、核心项目经历（按 STAR 组织）

### 项目 1：外设板功能开发（独立完成，最高优先级项目）

> 这是面试中的"重头戏"，务必讲透。

**背景（S）**：割草机器人需要感知温湿度、红外热成像、红外回冲信号，原方案由多板分担，链路混乱，需要统一整合到外设板。

**任务（T）**：独立完成外设板全部功能开发，使用 RT-Thread 框架，实现：
- AHT20 温湿度读取
- MLX90624 红外图像数据获取
- 红外回冲接收
- 通过 USB 转发图像/红外数据

**行动（A）**：经历多轮改版，硬件共出两版，软件更换多个方案：

- **第一版（硬件）**：温湿度、红外成像、红外接收都放外设板；红外成像经 USB 转发给算法板；红外接收与温湿度既接主板 MCU 也接外设板 MCU。**缺陷：外设板与主板之间没有通信手段**。
  - 该硬件版本下有两个软件版本：
    1. 所有读取都在外设板做，仅红外成像经 USB 转给主板；
    2. 红外接收与温湿度由主板读取，红外成像照旧。**发现红外与主板的同步信号冲突，方案放弃**。
- **第二版（硬件）**：温湿度、红外成像、红外接收全部在外设板完成，经 **UART 统一组包**发送给主板。
  - 关键参数：波特率 0.5 Mbps；红外成像占数据大头：**16 Hz ×（768 × 2）= 1536 Byte/帧**。

**结果（R）**：外设板功能稳定交付，成为主板数据源；锻炼了"硬件多版本 + 软件多方案"的迭代能力与跨板联调能力。

**追问准备（5W1H + 深挖）**：
- 为什么第一版要设计成"红外接收和温湿度同时接主板和外设板 MCU"？→ 冗余/职责划分权衡
- USB 转发的数据格式、端点、带宽够吗？IR 图像 16Hz 用 USB 还是 UART 更合适？→ 带宽对比：USB FS 12Mbps / HS 480Mbps vs UART 0.5Mbps
- UART 组包的帧格式（帧头/长度/校验/分包/粘包处理）？768×2 字节一帧怎么拆包？→ 一帧 1536B，按 MTU 分片、接收缓冲与状态机解析
- 同步信号冲突的根因是什么？怎么发现并规避的？→ 说明"跨板信号同步"的坑
- RT-Thread 里用的哪些机制？线程、信号量、消息队列、DMA、中断下半部？IR 数据量大时的线程优先级设计？

### 项目 3：IMU 二供器件迁移（最能体现排查能力的项目）

> 涉及老机器换新 IMU 的软件适配 + 接手离职同事半成品，踩坑极多，是"讲排查方法论"的绝佳素材。

**背景（S）**：为保证供应链，IMU 引入二供器件（ICM-45606），需要软件适配；同时存在"老机器更换新 IMU"与"新板子做适配（接手离职同事半成品）"两条线。

**任务（T）**：完成二供 IMU 在老机器与新板子上的软件适配，保证姿态解算（pitch/roll/yaw）正确。

**行动（A）与踩坑（含根因）**：

1. **拉错分支**：粗心拉到另一个机器的适配分支，导致 pitch 有约 20° 偏移。
   - 根因：最后发现根其实是同一个分支，只是拉错的那条分支有一些不兼容处理。
2. **移植后持续应激（后退）**：不管遥控哪个方向都后退（软件设计的错误上报，异常为"返回/抬起"）；上位机看数据正确。
   - 排查：接主板调试口打印，发现**加速度轴方向错位**，与算法对齐结构体结算后解决。
   - 根因分析（关键！）：算法板存在**多条解析链路**，但误以为只有一条。
     - 误以为算法板取的是外设板"解析拼接好"的数据，寄存器顺序不影响取数；
     - 实际算法板是**监听 SPI，直接从寄存器取数**，二供 IMU 寄存器取数顺序不同 → 数据错位；
     - 上位机数据显示正常，而上位机数据又由算法板上传，导致一度怀疑主板↔算法板通信问题，绕了弯路；也受同事误导。
     - 新增现象：跑机异常数据与"下错版本"时相似 → 原因竟是同事为排查上问题重新下了旧版本对比。
3. **数据波动大**：单独测试发现数据波动较大，但手册显示两者偏差应一致。
   - 根因：**滤波器未配置**。
   - 额外坑：前同事遗留**笔误 bug**——给一供（652）烧的代码，参数表却写的 607；查看 652 数据手册发现配置一样才定位。且此 607 并非三供 607（一个是 40607，一个是 42607）。
4. **新板子适配（RTT 板）**：pitch/roll 正常但 **yaw 角冻结**；旧板（裸机）正常。
   - 根因：**初始化少了校准函数**，姿态结算不更新（pitch/roll 走另一条链路所以正常）。RTT 导出的初始化函数名是 `data_init`（不带 mod 前缀），`data_init` 内没有校准。

**结果（R）**：完成二供 IMU 迁移，沉淀"多解析链路核对 + 与算法对齐结构体 + 滤波器配置核查"的方法论。

**追问准备**：
- SPI 监听是"侦听"模式还是片选复用？寄存器寻址方式？
- 结构体对齐：位域/字节序/对齐填充如何处理？算法端与 MCU 端如何约定？
- IMU 滤波器（DMP/低通）如何配置？为什么没配会导致波动？
- 校准函数的作用（bias/scale、温度补偿）？`data_init` 缺校准为何只影响 yaw？
- 如何避免"误以为只有一条链路"这类认知盲区？→ 答：先画出完整数据流图，再定位断点。

## 三、问题排查案例库（STAR + 根因，面试重点）

### 案例 1：电机堵转（最常见的 TB，含多场景）

**现象**：刀盘电机 / 轮子电机堵转，触发过温保护停机。

**场景分类**：
1. **轮子电机（多数）**：导航异常，碰到障碍未识别、未避障。嵌入式只执行算法板下发的速度指令，没避开就一直怼障碍物 → 卡住堵转。
2. **轮子电机（少数）**：带集草框的机器，在墙边/树旁转弯时集草框撞墙/撞树被卡 → 轮子堵转。
3. **刀盘电机（多数）**：割到硬物，正常堵转报错。
4. **刀盘电机（少数）**：划过水坑，刀盘堵转。
5. **轮子正常堵转但产品不认**（误报/判定阈值问题）。

**分析要点**：
- 区分"执行层正常执行指令"与"上层没避障"——嵌入式只对下发的速度负责，堵转根因常在上层（算法导航）。
- 堵转 → 电流增大 → MOS 管温升 → 过温报错，是典型故障链。
- 多个 TB 要合并分析（相同日志特征归因到同一根因）。

---

### 案例 2：设备"悬空"误报（抬起检测）

**现象**：测试报"设备悬空/抬起"，实际并未抬起。

**场景**：
1. **正常颠簸误报**：抬起状态定义（1=左抬，2=右抬，3=双侧抬起），测试人员"状态不为 0 就判抬起"，但正常路面颠簸会瞬时触发。
2. **有坡度土坑**：进入有坡度土坑被判定悬空。但符合设计——**超过 22.5° 就会报悬空**，属设计行为，需与测试对齐预期。
3. **一批机器的结构问题**：抬起检测结构有问题的批次机器频繁误报，新版本修复。
4. **被其他异常状态影响**：充电桩上桩异常，机器一直怼桩，充电桩有坡度 → 容易触发抬起报错。

**分析要点**：
- 涉及"判定阈值 vs 用户预期"的边界问题，需要与测试/产品对齐判定标准。
- 抬起的传感器（IMU 角度？）与结构件联动。

### 案例 3：客诉——右轮突然失控，左轮正常

**现象**：客户反馈电机运行中右轮突然失控，左轮正常。

**排查**：
- 询问客户得知"轮子有力"，排除电机本身问题 → 怀疑通信。
- 找负责电机同事确认：**之前 CAN 的终端电阻有问题**，后续硬件版本已更新；该板子疑似老版硬件。

**结论**：老版本硬件 CAN 电阻问题导致右轮通信异常 → 失控。硬件版本更新后解决。

### 案例 4：蜂鸣器"勿扰模式"开机失效（边缘功能开发）

**需求背景**：用户开启勿扰模式后蜂鸣器全程不发声；但**开机阶段**算法板还没起来，无法下发静音指令，导致开机发声。

**方案**：改动最小化——开启勿扰时把**静音标志写入 FLASH**，每次发声前**读 FLASH** 判断是否发声。

**排查过程（重要！体现跨组联调能力）**：
- 原算法板逻辑（应用侧说法）：勿扰模式"不发任何信息"；主板逻辑：需收到"使能标志 + 音量≠0"才发声。
- 先验证读 FLASH 正常：收上位机音量 0 → 静音标志写 FLASH → 每次发声前读 FLASH。逻辑简单，正常没问题。
- 但**开机时功能不生效**。拆机对 UI 板单独调试、串口打印：FLASH 标志确认写进去了，但**应用不管开没开勿扰，关机前都会把音量调为 100 并发送使能标志** → 写 FLASH 失效。
- 解决：与应用沟通，升级一个"开启勿扰后发送**失能标志**"的功能；主板逻辑改为**收到失能或音量 0 都写静音标志**。
- 附加坑：当时算法板版本是**特调版**，导致后续版本更新、研发自测时同机器同代码却不再生效 → 教训：联调时注意版本对齐与可复现性。

**技术点延伸**：FLASH 读写的磨损均衡 / 掉电保护 / 写失败处理。

### 案例 5：电机老化测试停机（电池过温保护）

**现象**：老化程序（升降电机最高↔最低往复、刀盘 4000 rpm）运行后停机。

**排查**：
- 晚上开测第二天停机；重烧代码能跑但过一会又停 → 报**电池欠压**错误。
- 询问同事：电池有**过温保护**，过温后**切断输出**。
- 改直流供电，刀盘仍报过温 → 将刀盘转速从 4000 调到 **2000 rpm**，老化程序正常运行。

**结论**：长时间满载导致电池/电机过温，触发保护；降载后恢复正常。体现"大功率负载下热管理"的意识。

---

### 案例 6：回充上桩异常（三个 TB 关联分析，记忆深刻的一次排查）

**现象**：三个 TB，两个描述类似且有关联（待机时触发堵转），一个报悬空；故障描述上看似无关，实际内容关联。

**具体经过**：两个 TB 日志表现一致——充电桩上出现"抬起"（实际未抬起）+ 多次堵转 → MOS 管温度多次升高 → 过温报错。

**排查**：怀疑上桩过程异常。从视觉反馈看并未碰到充电、运行模式一直显示"回充导航"、未充上电 → 推测机器一直**尝试往前怼充电桩**导致堵转。后找到的悬空报错机器同样现象，三个 TB 是同一台机器 → 基本确认**上桩异常**。

**验证**：交测试交叉验证——好机器上坏桩、坏机器上好桩，区分是机器问题还是桩问题。**版本更新后无异常**。

**方法论**：多 TB 合并、视觉/日志/状态机多信号交叉印证、隔离变量（交叉验证）。

---

### 案例 7：机器"搬回公司就不能用"（工厂→公司环境差异）

**现象**：工厂正常，搬回公司后不能用；上位机显示主板相关信息都未上传。

**排查**：
1. 先怀疑充电把机器冲坏（之前有几例）→ 万用表测充电触点正常，排除。
2. 怀疑通讯损坏（主板数据 → UI 板 → 算法板上传链路）→ 示波器看主板波形确实不正常 → 移交硬件。
3. 硬件定位：**有一个管子烧了**，怀疑工人**带电插拔**导致。

**教训**：多链路数据流要有全局视图；波形级定位把问题从"软件怀疑"收敛到"硬件损坏"。

### 案例 8：产测问题——下桩后停机、时间戳缺失

**现象**：机器跑机时下桩后停机；嵌入式按下发速度正常执行，但**时间戳没有显示**。

**排查**：
- 转算法排查：发现有一个 **ODO 同步信号未取到**，算法是从应用侧取得。
- 询问应用：该信号是"主板这边上发"（实际应为算法板下发 → 主板中断处理 → 重新上传），但排查中需看两边板子的信号。
- 拆机示波器量测 → **排线问题**。

**结论**：同步信号链路中断（排线），导致下桩时序异常停机。

当前外设板主要是进行数据的发送，接受数据只接受ota的数据，采用的是中断，每收到一个字节进一次中断，然后拼成完整帧后送入回调处理函数。接受数据也是用的同一套通信框架，有对应的帧头帧尾以及mod_id和对应mod的长度以及crc校验，能避免出现半包粘包的问题。校验错误就不会接受该包数据，接受设了最长超时时间180ms，超时会进行退出，重复包暂时没有相关处理。当前板子只管发送

5. ESP32双电机FOC项目使用的电机、驱动器、电流及位置传感器分别是什么？控制周期是多少？ADC采样如何和PWM同步？FreeRTOS任务划分及优先级是什么？有没有运行视频或电流波形？
2208电机、驱动是套件、INA240A  AS5600 磁编码器。控制周期电流环20k，速度环1k，位置环200hz。1.节拍同步：同一个 20kHz 定时器，TIMG1 硬件定时器以 20kHz（50µs）触发 foc_timer_isr_entry → foc_isr。电流采样、电流环 PID、SVPWM 输出全在这一次 ISR 内顺序执行，没有跨周期缓冲，所以天然是同一节拍——不存在"采样靠别的时钟"的问题。2. 采样点对齐：软件延时到 SVPWM 下管导通中点。这是关键。PWM 是中心对齐（，三相占空比关于周期中点对称，在周期中点附近存在一个"三相下管全导通"的公共窗口——此刻相电流经采样电阻方向稳定、无开关瞬态，是理想的电流采样点。rtos划分了3个任务，一个是电机控制，主要包括as5600位置的更新以及速度环和位置环的计算和接受串口任务发过来的简短指令，一个是解析串口指令任务，这部分是通过解析上位机传过来的指令，然后通过队列发给电机控制任务，还有一个是监控任务，周期打印心跳以及电机状态。

6. YMODEM升级过程中，传输中断、Flash写入中断、整包校验失败、新程序启动失败时分别如何恢复？目前是否真正做过自动回滚？
一、传输中断（包括拔线/掉电/超时）：每包有超时，CRC/序列/超时错误 → NAK + 重试，最多 10 次；超限放弃，，boot 进入 while(1) 3 秒后重试。
掉电/拔线重启：接收全程 ota_state 始终是 IDLE（RECEIVING/VERIFY 是 dead code，从未置位），只有全部成功后才会写 COMPLETE。所以重启后 boot_decision 走 IDLE 分支 → 活跃槽有效 → 直接跳旧固件。目标槽残留的半个镜像不影响任何事——元数据（size/crc）还是旧的，下次 OTA 会重新擦除覆盖。
二、Flash 写入中断
F4 的 Word/Byte 编程是原子操作，不存在"写一半"，要么整字完成要么硬件报错。每字写完还有回读校验。
写入失败 ，flash返回YMODEM_ERR_FLASH，中止，活跃槽不变。
擦除/编程执行中掉电，该扇区内容不确定，但只发生在非活跃槽；参数区掉电由 append-only 日志兜底（写半条 → CRC 不匹配 → load_latest 跳过取上一条）。
三、整包校验失败
两层：
逐包 CRC16（协议层）：ymodem.c:101 —— 每 1024B 包校验，失败 NAK 重试。
整包 CRC32 + reset-handler 防错包：ota.c:94-103 —— 收到后检查镜像链接地址是否落在目标槽（防发错 bin）；算 CRC32 后记录到元数据。
还有一个关键点：ota算完 CRC32 后没有立即与期望值比较，直接翻转 active。真正的整包校验被推迟到下次启动的 boot_decision COMPLETE 分支。
CRC32 mismatch → boot_count 递增 → 未超限 NVIC_SystemReset 重试 → 超限 rollback_to_other() 切回旧槽。这是设计上的两阶段校验：传输层 CRC16 已保证数据完整性，boot 阶段的 CRC32 是防“元数据错配或半写入”的最终闸门。
四、新程序启动失败
boot 保持 COMPLETE + 启动 看门狗 + 跳转。App 需在窗口内喂狗以及检查活跃槽是否正确。
崩溃/卡死 → 不喂狗 → IWDG 复位 → boot_count=2 → 再试 → …→ 超 3 次 → rollback_to_other() 切回旧槽。
正常启动 → 确认 → 结束观察窗口，运行期崩溃由 IWDG 复位（不回滚）。
当前还未做过。

# C 语言编译流程与内存布局（面试复习 · MCU 为主）

> 适用方向：嵌入式软件（MCU / RTOS / 裸机）
> 主线聚焦 **MCU**（物理地址、Flash/RAM 分离、交叉编译、链接脚本、启动文件）；Linux 只保留最基本概念。
> 本文件回答两个高频问题：**① 一段 C 代码从源文件到烧录镜像经历了什么；② 程序运行时各变量/代码分别放在 Flash/RAM 的哪里。**

---

## 第一部分：C 语言编译流程（MCU 视角）

### 1.1 总览（一张图记住四阶段）

```
main.c (文本源码)
    │
    ▼  [1] 预处理 Preprocessing   (arm-none-eabi-gcc -E)
main.i (展开后的文本，仍是 C 源码)
    │
    ▼  [2] 编译 Compilation      (arm-none-eabi-gcc -S)
main.s (ARM 汇编代码)
    │
    ▼  [3] 汇编 Assembly          (arm-none-eabi-gcc -c)
main.o (可重定位目标文件，机器码 + 符号表 + 重定位信息)
    │
    ▼  [4] 链接 Linking           (arm-none-eabi-ld，用 .ld 链接脚本)
main.elf ──(objcopy)──> main.bin / main.hex (可烧录镜像)
```

**一句话总结**：预处理处理 `#` 指令，编译把 C 翻译成 ARM 汇编，汇编把汇编翻译成机器码并生成目标文件，链接按链接脚本把多个目标文件合并、解析符号、重定位成 `.elf`，最后 `objcopy` 转成可烧录的 `.bin`/`.hex`。

对应 GCC 常用选项（PC 上 gcc 与交叉 gcc 同名选项一致）：

| 阶段 | 命令 | 输入 | 输出 |
|------|------|------|------|
| 预处理 | `gcc -E main.c -o main.i` | `.c` | `.i` |
| 编译 | `gcc -S main.i -o main.s` | `.i` | `.s` |
| 汇编 | `gcc -c main.s -o main.o` | `.s` | `.o` |
| 链接 | `gcc main.o -T link.ld -o main.elf` | `.o` + 库 | `.elf` |

> `arm-none-eabi-gcc main.c -o main.elf` 一条命令内部依次完成四步，中间文件默认不保留。嵌入式链接时通常用 `-T link.ld` 指定链接脚本，用 `-Wl,-Map=main.map` 生成 map 文件。

---

### 1.2 预处理（Preprocessing）

**做什么**：处理所有以 `#` 开头的指令，本质是"文本替换"，不涉及语法检查。

| 指令 | 作用 |
|------|------|
| `#include` | 把被包含的头文件内容**原样展开**插入到当前位置 |
| `#define` | 宏定义，做**纯文本替换** |
| `#if / #ifdef / #ifndef / #elif / #else / #endif` | 条件编译，按条件保留或删除代码 |
| `#undef` | 取消宏定义 |
| `#pragma` | 编译器特定指令（如 `#pragma pack`） |
| `#error / #warning` | 编译时报错/告警 |
| 其他 | 删除注释；插入行号与文件名标记（`#line`），方便报错定位 |

**MCU 常见用法 / 坑**：

- 宏是**文本替换，不做类型检查、不求值**。经典坑：

  ```c
  #define SQUARE(x) x * x
  int a = SQUARE(1 + 2);   // 展开为 1 + 2 * 1 + 2 = 5，而不是 9！
  ```
  正确写法：`#define SQUARE(x) ((x) * (x))`。

- **寄存器地址 / 位操作宏**是 MCU 头文件的核心：

  ```c
  #define GPIOA_BASE  ((uint32_t)0x40020000)
  #define BIT(n)      (1UL << (n))
  ```

- 条件编译做**硬件版本适配 / 调试开关**：

  ```c
  #ifdef USE_ICM45606      // 二供 IMU 适配
      // ICM-45606 相关配置
  #else
      // 默认 ICM-42652 配置
  #endif
  ```

- `#include "xx.h"`（先当前目录）与 `#include <xx.h>`（编译器/系统头文件目录）的区别；头文件防重复包含用 `#ifndef/#define/#endif` 或 `#pragma once`。

---

### 1.3 编译（Compilation，狭义）

**做什么**：把预处理后的 C 代码翻译成**目标平台汇编代码**（MCU 场景是 ARM Cortex-M 汇编）。

内部子步骤：

1. **词法分析**：把字符流切成 token。
2. **语法分析**：按语法规则组成**语法树（AST）**。
3. **语义分析**：**类型检查**、作用域检查、类型转换等。
4. **中间代码生成与优化**：生成 IR，做常量折叠、死代码消除、内联等优化。
5. **目标代码生成**：把 IR 翻译成 ARM 汇编。

**关键点**：

- 语法错误、类型不匹配、未声明变量大多在这一步报出。
- 优化由 `-O0 / -O1 / -O2 / -O3 / -Os` 控制。**MCU 调试阶段常用 `-O0`**，避免变量被优化掉导致在线调试看不到值；`-Os` 侧重减小代码体积（Flash 紧张时用）。
- **volatile 与优化**（嵌入式高频）：优化可能把"反复读同一个地址"的变量缓存到寄存器，硬件寄存器/中断共享变量必须加 `volatile`，否则被优化出错。

---

### 1.4 汇编（Assembly）

**做什么**：把汇编代码翻译成**机器码**，生成**可重定位目标文件**（`.o`，MCU 场景同样是 ELF 格式）。

目标文件 `.o` 通常包含：

| 组成 | 作用 |
|------|------|
| 机器指令 | 编译/汇编后的二进制代码 |
| 数据 | 已初始化的全局/静态变量的初始值 |
| **符号表（Symbol Table）** | 记录本文件定义的符号（函数名、全局变量名）和引用的外部符号 |
| **重定位信息（Relocation Entry）** | 记录哪些地址需要在链接时被修正 |

**关键点**：

- `.o` 里的地址是**相对的、未定的**，函数调用和全局变量引用还是"符号引用"，具体地址等链接时确定。
- 常用分析工具（交叉版带 `arm-none-eabi-` 前缀）：`objdump`（反汇编）、`readelf`、`nm`（符号表）、`size`（各段大小）。

---

### 1.5 链接（Linking）

**做什么**：按**链接脚本**把多个 `.o` 和库合并成一个 `.elf` 镜像。

两个核心任务：

1. **符号解析（Symbol Resolution）**：把每个"符号引用"和唯一一个"符号定义"关联（如 `main.c` 调 `foo()`，在别的 `.o` 或库中找到 `foo` 定义）。
2. **重定位（Relocation）**：把符号引用地址修正为最终运行时地址（合并段、按链接脚本分配地址、回填地址）。

**常见链接错误**：

- `undefined reference to 'xxx'`：有声明无定义，或没链接对应库。
- `multiple definition of 'xxx'`：多个文件定义同名全局符号。

**静态链接 vs 动态链接（了解即可）**：

| 对比项 | 静态链接 | 动态链接 |
|--------|----------|----------|
| 时机 | 链接时把库代码**全部拷进**产物 | 运行时才加载共享库 |
| 产物大小 | 大 | 小 |
| 运行依赖 | 不依赖外部库 | 依赖 `.so`/`.dll` |
| **MCU** | **MCU 基本只有静态链接** | 需 OS 支持动态加载，MCU 无 |

---

### 1.6 链接脚本（Linker Script，`.ld` / `.lds`）—— MCU 核心

MCU 的 Flash 和 RAM 是分离的物理存储器，链接器需要知道各段放哪个地址，这由链接脚本决定。

```ld
MEMORY
{
    FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 256K
    RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 64K
}

SECTIONS
{
    .isr_vector : { *(.isr_vector) } > FLASH   /* 向量表 */
    .text       : { *(.text*) } > FLASH         /* 代码 */
    .rodata     : { *(.rodata*) } > FLASH       /* 只读数据 */
    .data       : { *(.data*) } > RAM AT > FLASH/* 初值存 Flash，运行时在 RAM */
    .bss        : { *(.bss*) } > RAM            /* BSS，启动时清零 */
    .heap       : { ... } > RAM                 /* 堆 */
    .stack      : { ... } > RAM                 /* 栈（栈顶） */
}
```

- `> RAM AT > FLASH`：`.data` 的**加载地址（LMA）在 Flash**（初始值存 Flash），**运行地址（VMA）在 RAM**（运行时变量在 RAM），启动时由启动代码把初始值从 Flash 拷到 RAM。
- `MEMORY` 里 `ORIGIN`/`LENGTH` 必须与芯片数据手册一致（Flash 基地址、RAM 基地址和大小），否则程序跑飞。

---

### 1.7 交叉编译与工具链（嵌入式重点，高频考点）

**概念**：在一种平台（通常 x86 PC）上编译生成**另一种平台**（ARM Cortex-M MCU）能运行的代码。

- **本地编译（Native）**：编译平台 = 运行平台（PC 上 gcc 编译 PC 程序）。
- **交叉编译（Cross）**：编译平台 ≠ 运行平台（PC 上 `arm-none-eabi-gcc` 编译 MCU 固件）。

**为什么 MCU 要交叉编译**：MCU 资源有限、不适合在芯片上直接编译，用性能强的 PC 编译后烧录到 MCU。

常见 ARM Cortex-M 工具链：

| 工具 | 作用 |
|------|------|
| `arm-none-eabi-gcc` | 编译器（compile → assemble → link） |
| `arm-none-eabi-ld` | 链接器 |
| `arm-none-eabi-objcopy` | 格式转换 `.elf` → `.bin` / `.hex` |
| `arm-none-eabi-objdump` | 反汇编、查看目标文件 |
| `arm-none-eabi-nm` | 查看符号表 |
| `arm-none-eabi-size` | 查看各段大小 |

**`elf → bin/hex` 的区别（可追问）**：

- `.elf`：含调试信息、符号表、段信息，**不能直接烧录**，供调试器（J-Link/ST-Link）用。
- `.bin`：纯二进制镜像，**无地址信息**，从固定基地址（如 `0x08000000`）烧录。
- `.hex`：Intel HEX 格式，**带地址信息**，按记录烧录，适合不同起始地址/OTA 场景。

---

### 1.8 编译产物与 map 文件（MCU 实战）

**`.map` 文件**是链接后生成的重要排查文件，能看：

- 各段（`.text`/`.data`/`.bss`）的**起始地址和大小**。
- 每个**函数、全局变量的最终地址**。
- **Flash/RAM 占用是否超限**（是否溢出）。
- 排查"程序跑飞/硬 fault"时定位符号地址、检查栈是否越界。

生成方式：`-Wl,-Map=output.map`。`size` 命令可快速看各段总大小。

### 1.9 编译流程高频面试问答

- **Q：`gcc` 一条命令编译时内部发生了什么？** → 依次执行预处理、编译、汇编、链接四步。
- **Q：`.o` 文件是什么？** → 可重定位目标文件，含机器码、符号表、重定位信息，地址未定。
- **Q：`undefined reference` 是什么原因？** → 链接阶段符号解析失败：有声明无定义，或没链上库。
- **Q：交叉编译是什么？为什么 MCU 需要？** → 见 1.7。
- **Q：链接脚本（`.ld`）的作用？** → 规定 Flash/RAM 地址范围和各段放置位置。
- **Q：`.elf` 和 `.bin`/`.hex` 的区别？** → 见 1.7。
- **Q：宏和函数区别？** → 宏是预处理文本替换，无类型检查、可能有副作用；函数有类型检查与独立调用开销。

## 第二部分：C 程序内存布局（MCU 为主线）

### 2.1 MCU 内存布局总览（物理地址，Flash/RAM 分离）

MCU **没有 MMU**，用的是**物理地址**；Flash 和 RAM 是两块独立的物理存储。典型 Cortex-M 分布：

```
Flash（非易失，掉电不丢）          RAM（易失，掉电丢失）
┌────────────────────────┐ 0x08000000   ┌────────────────────────┐ 0x20000000
│ 向量表 Vector Table     │               │ .data（运行时，从Flash拷来）│
│ .text 代码              │               │ .bss（启动时清零）        │
│ .rodata 只读数据         │               │ Heap（向上增长 ↑）        │
│ .data 初始值（LMA）      │               │ Stack（向下增长 ↓，栈顶）  │
└────────────────────────┘               └────────────────────────┘
```

**核心记忆**：

- **代码和常量在 Flash**：`.text`、`.rodata`、向量表、`.data` 的初始值副本。
- **变量在 RAM**：`.data`（运行时）、`.bss`、堆、栈。
- 栈顶通常指向 **RAM 末尾**，向下增长；堆从 `.bss` 之后向上增长，两者相对生长。

---

### 2.2 各段详解（都标注在 MCU 中的位置）

#### （1）`.text` —— 代码段（Flash）

- 存放**机器指令**（所有函数体）。
- 属性：只读 + 可执行。
- MCU：放 **Flash**（`0x08000000` 起，向量表之后）。

#### （2）`.rodata` —— 只读数据段（Flash）

- 存放 `const` 全局/静态变量、字符串字面量、`switch` 跳转表。
- MCU：放 **Flash**，省 RAM。

  ```c
  const int version = 3;      // Flash .rodata
  char *p = "hello";          // "hello" 在 Flash .rodata
  ```

#### （3）`.data` —— 已初始化数据段（初始值在 Flash，运行时在 RAM）

- 存放**已初始化且初值非 0** 的全局/static 变量。
- **占用 Flash 空间**（保存初始值），运行时占用 RAM。
- MCU：初始值存 Flash，上电由启动代码拷贝到 RAM。

  ```c
  int global = 10;            // .data（初值 10 在 Flash，运行时变量在 RAM）
  static int s = 5;           // .data
  ```

#### （4）`.bss` —— 未初始化/零初始化数据段（RAM）

- 存放**未初始化**或**初始化为 0** 的全局/static 变量。
- **不占用 Flash**（只记大小，不存初值），启动时统一清零。
- BSS = **Block Started by Symbol**。

  ```c
  int global2;                // .bss
  static int s2;              // .bss
  int arr[100] = {0};         // .bss（全 0）
  ```

> **高频考点：`.data` 和 `.bss` 的区别（用 Flash/RAM 记）**
> - `.data` 存非 0 初值，**既占 Flash（存初值）又占 RAM（运行时）**。
> - `.bss` 只记录大小，**不占 Flash，只占 RAM**（启动时清零）。
> - `size` 看到的 `.text + .data` 大致反映 Flash 占用，`.data + .bss` 反映 RAM 占用（不含堆栈）。

#### （5）堆 Heap —— 动态内存（RAM）

- `malloc/calloc/realloc` 分配，`free` 释放。
- 手动管理，向上增长。
- MCU：需在链接脚本/启动文件配置堆大小（`HEAP_SIZE`），**硬实时系统慎用**（分配时间不确定 + 内存碎片）。

#### （6）栈 Stack —— 自动变量（RAM）

- 存放**局部变量、函数参数、返回地址、被调函数保存的寄存器**。
- 编译器自动管理，向下增长，分配极快（移动 SP）。
- MCU：大小有限（链接脚本定），**越界/过深递归会栈溢出**，可能覆盖 `.data`/`.bss`。

---

### 2.3 变量存储位置总结（高频考点，务必背熟）

| 变量类型 | 存储位置 | MCU 所在介质 | 生命周期 |
|----------|----------|-------------|----------|
| 局部变量 | 栈 | RAM | 函数内 |
| 函数参数 | 栈或寄存器 | RAM / CPU 寄存器 | 函数内 |
| 全局变量（已初始化非 0） | `.data` | Flash 存初值 + RAM 运行 | 整个程序 |
| 全局变量（未初始化/0） | `.bss` | RAM | 整个程序 |
| 局部 `static` 变量 | `.data`/`.bss` | Flash/RAM 同上 | 整个程序（作用域仅本函数） |
| 全局 `static` 变量/函数 | `.data`/`.bss`/`.text` | 同上 | 整个程序（作用域仅本文件） |
| `const` 全局变量 | `.rodata` | Flash | 整个程序 |
| 字符串字面量 | `.rodata` | Flash | 整个程序 |
| `malloc` 分配的内存 | 堆 | RAM | 手动控制 |
| 指针变量本身 | 看定义位置 | 局部在 RAM 栈，全局在 `.data`/`.bss` | 看定义位置 |

**关键辨析**：

- **`const` 局部变量不一定在 Flash**：`const int a = 5;` 在函数内仍可能放**栈（RAM）**，`const` 只是编译期"只读"约束；`const` 全局/静态变量才通常放 `.rodata`（Flash）。
- **字符串字面量不可修改**：`char *p = "abc"; p[0] = 'x';` 是未定义行为（`"abc"` 在 Flash 的 `.rodata`）。要可修改用字符数组 `char s[] = "abc";`（拷贝到栈上数组）。

---

### 2.4 启动流程（复位后到 main 之前，高频考点）

1. 上电复位，PC 跳转到**复位向量**指向的启动代码（`startup_xxx.s` 的 `Reset_Handler`）。
2. 设置**栈指针 SP/MSP**（向量表首项存的是**初始栈顶地址**）。
3. 拷贝 `.data`：把初始值从 **Flash 拷到 RAM**（LMA→VMA）。
4. 清零 `.bss`：把 `.bss` 区域全部写 0。
5. （可选）初始化时钟、外部 RAM、C 库运行时环境。
6. 调用 `main()`。

> **向量表（Vector Table）**：位于 Flash 最前端，第一项是**初始栈指针（MSP）**，第二项是**复位向量（Reset_Handler 地址）**，后面依次是各中断服务函数（ISR）入口地址。中断发生时硬件按中断号查表跳转。

> 这解释了为什么"全局变量有初始值"能生效：初始值固化在 Flash 里，上电由启动代码搬运到 RAM；未初始化/0 的变量靠清零 `.bss` 得到确定初值 0。

---

### 2.5 栈与堆深入对比（MCU 高频考点）

| 对比项 | 栈 Stack | 堆 Heap |
|--------|----------|---------|
| 管理方式 | 编译器自动 | 程序员手动 `malloc/free` |
| 分配速度 | 极快（移动 SP） | 较慢（找空闲块） |
| 大小 | 小（KB 级，链接脚本定） | 可配置，可增长 |
| 增长方向 | 向下 | 向上 |
| 生命周期 | 函数内自动 | 程序员控制 |
| 常见问题 | **栈溢出**（大局部数组/深递归） | **内存泄漏、内存碎片** |
| 实时性 | 确定，零抖动 | `malloc` 耗时不确定，硬实时大忌 |

**栈溢出**：局部变量过大（`char buf[10000]`）或递归过深，栈指针越过栈底，可能覆盖 `.data`/`.bss`，引发不可预测崩溃（硬 fault）。MCU 避免方法：配置足够栈、大缓冲区用静态数组、限制递归、栈溢出检测。

**内存碎片**：反复 `malloc/free` 不同大小块后，堆里出现不连续小空洞，导致"总空闲够但分配不出大块"。硬实时系统（电机控制、CAN 通信）**通常禁止动态内存**，改用静态数组预分配。

**嵌入式铁律（结合实习）**：需要实时性和稳定性的任务用**静态分配**（全局/静态数组），不用 `malloc`。对应 FreeRTOS/RT-Thread 创建任务栈：优先 `xTaskCreateStatic`（静态数组栈），避免 `xTaskCreate`（内部 `malloc`）。

### 2.6 Linux 进程内存布局（基本了解即可）

> MCU 面试一般不深究 Linux，记住下面这个"通用段布局"就够。Linux 进程有 **MMU 虚拟内存**，和 MCU 物理地址不同。

```
高地址
┌──────────────┐
│ 内核空间       │
├──────────────┤
│ 栈 Stack(↓)  │
│   （空洞）    │
│ mmap 映射区   │
│ 堆 Heap(↑)   │
│ .bss         │
│ .data        │
│ .rodata      │
│ .text        │
└──────────────┘
低地址
```

**与 MCU 的区别（一句话）**：Linux 每个进程有独立的虚拟地址空间、有内核/用户态之分、支持动态链接库（mmap 区）；MCU 是裸物理地址、代码和常量固化在 Flash、变量在 RAM，几乎没有动态链接。

### 2.7 内存布局高频面试问答

- **Q：MCU 里代码和变量分别放哪？** → 代码/常量（`.text`/`.rodata`）在 Flash，变量（`.data`/`.bss`/堆/栈）在 RAM。
- **Q：`.bss` 为什么比 `.data` 省 Flash？** → `.bss` 只记大小不存初值，启动清零；`.data` 要存非 0 初值。
- **Q：全局变量和局部变量区别？** → 存储位置（`.data`/`.bss` vs 栈）、生命周期（全程 vs 函数内）、默认初值（全局 0，局部垃圾值）。
- **Q：`static` 关键字作用？** → ① 局部 `static`：生命周期全程、只初始化一次、作用域不变；② 全局 `static`：限制作用域在本文件；③ `static` 函数：只本文件可见。
- **Q：`const` 变量一定在 Flash 吗？** → 不一定，局部 `const` 可能在栈（RAM）；全局 `const` 通常在 `.rodata`（Flash）。
- **Q：栈和堆区别？增长方向？** → 见 2.5。
- **Q：为什么全局变量默认 0，局部变量不是？** → 全局变量在 `.bss`，启动统一清零；局部变量在栈，内容是上次残留的垃圾值。
- **Q：栈溢出怎么发生？** → 局部数组过大或递归过深，栈空间耗尽，可能覆盖 `.data`/`.bss`。
- **Q：复位后到 `main()` 之前发生了什么？** → 设 SP → 拷贝 `.data`（Flash→RAM）→ 清零 `.bss` → 调 `main`。
- **Q：什么是内存泄漏？** → 堆上 `malloc` 后未 `free`，内存无法回收，长期运行耗尽。

## 第三部分：一页速记（考前过一遍）

1. **编译四阶段**：预处理（`#` 文本替换）→ 编译（C→汇编）→ 汇编（汇编→机器码/`.o`）→ 链接（合并、符号解析、重定位）。
2. **`.o` 三段关键内容**：机器码、符号表、重定位信息。
3. **链接两大任务**：符号解析 + 重定位；MCU 用 `.ld` 脚本规定 Flash/RAM 地址。
4. **MCU 介质归属**：代码/常量在 Flash，变量在 RAM。
5. **`.data` vs `.bss`**：前者存非 0 初值（占 Flash+RAM），后者只记大小（启动清零，只占 RAM）。
6. **变量归属**：局部/参数→栈(RAM)；全局/静态已初始化→`.data`；未初始化/0→`.bss`；const 全局/字符串→`.rodata`(Flash)；`malloc`→堆(RAM)。
7. **栈 vs 堆**：栈自动、快、小、向下、会溢出；堆手动、慢、大、向上、会碎片/泄漏。
8. **MCU 启动**：复位→取初始 SP→设 SP→拷贝 `.data`（Flash→RAM）→清零 `.bss`→调 `main`。
9. **硬实时铁律**：要实时/稳定 → 静态分配，不用 `malloc`。
10. **交叉编译**：PC 上用 `arm-none-eabi-gcc` 生成 MCU 固件，`objcopy` 转 `.bin`/`.hex`。
